# Smoke evidence: v0.2.5 (no VPN, bridge correctness)

**Date:** 2026-11-18
**Host:** `sonic`, Windows 11, WSL 2, VPN not running
**Release under test:** `v0.2.5` (`32fb511`; alpine 3.24 digest bump + go 1.26.11, x/sys 0.50.0, gvisor-tap-vsock v0.9.0, empty `/etc/ld.so.conf.d`)

## Gates

### 1. HTTPS through the bridge

From the sibling distro:

```
$ curl -sI https://1.1.1.1 | head -1
HTTP/2 301
```

PASS.

### 2. Bulk download

```
$ nstat -n ; curl -so /dev/null -w '%{http_code} %{size_download} %{speed_download}\n' https://proof.ovh.net/files/10Mb.dat ; nstat TcpInSegs TcpExtTCPDSACKOldSent
200 10485760 9092182
#kernel
TcpInSegs                       49954              0.0
TcpExtTCPDSACKOldSent           42137              0.0
```

Full 10 MB, ~73 Mbit/s, same throughput as v0.2.4. PASS.

## Spurious retransmission (not a gate)

`TcpExtTCPDSACKOldSent / TcpInSegs` = 42137 / 49954 = 84%, against 83% on v0.2.4 (`docs/smoke-2026-10-04.md`, 5 MB download). gvisor-tap-vsock v0.9.0 moves gvproxy to gVisor `20260413` (v0.8.9 shipped `20240916`), and the duplicate rate is unchanged, so the newer gVisor does not fix it. Tracked in TODO (Backlog).

## Not covered

VPN-bypass was not exercised at this event (VPN not running). gvproxy code changed with v0.9.0; the gvforwarder spawn contract (`cmd/vm`, `pkg/net/stdio`, `pkg/transport/dial_linux.go`) is byte-identical to v0.8.9.
